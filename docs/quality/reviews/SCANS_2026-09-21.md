# The two mechanical scans (2026-09-21)

Section 26 produced five findings, and three of them were **the same
sentence**: *a failure that looks like an empty result.* One sentence found
three times by hand is a sentence worth looking for by machine. Two scans came
out of that, and this is what they found — and, just as important, what they
cannot find.

---

## Scan 1 — every handler that answers a failure with a falsy value

**The question:** which `except` blocks `return None` / `return False` /
`return []` / `return {}` / `return ''`?

**33 hits.** Most are harmless, and for a reason worth writing down: the
caller **refuses** on a falsy answer, and nothing is lost by refusing. A
falsy answer is only dangerous where falsy means *go ahead*.

One finding: **E6** — `_get_disallowed_action_reason` answered "no reason to
refuse" when the container configuration could not be read, so a scheduled
action touched a container without confirming it was still allowed. Recorded
as SPEC.md **B14**, fixed in `2a156f4`.

1 of 33 is not a poor yield. The other 32 are now *known* to be harmless
rather than unexamined, which is the difference the programme exists to make.

---

## Scan 2 — handlers that cannot catch a DDC exception

**The question:** `services/exceptions.py` defines `DDCBaseException(Exception)`
with some fifty subclasses. Where does a narrow `except (...)` tuple sit in
front of a call that raises one of them?

This scan came from a pattern the review kept meeting: **a repair that made
one thing safe made another thing fragile.** Review D1 gave
`_heal_if_lagging` a `raise` so that a mech snapshot lagging behind the event
log could no longer quietly bury a donation. Correct — and every handler
written before D1 that calls into the mech now has a hole in it, on paths
nobody re-read.

**11 hits, reduced to 9 after two were judged duplicates. All nine judged:**

| # | Where | Verdict |
|---|---|---|
| — | `app/bot/token.py` ×2 | **Fixed**, `ea526a6` (E10/E11) |
| — | `app/bot/startup_steps/power.py` | **Fixed**, E8 — the power gift took the seven steps after it down |
| — | `app/bot/startup_steps/sequence.py` | **Fixed**, E9 — one failed step stopped all the others |
| — | `config_form_parser_service.py` | **Fixed**, E10 |
| #1 | `main_routes.py:461` `save_spam_protection` | **False positive** — see below |
| #4 | `donation_config.py:28` `set_donation_disable_key` | **Fixed**, E13 (`0927d2a`) — no production caller, pinned anyway |
| #6/#7 | `donation_message_service.py:101` | **Fixed**, E12 (`fc3ca28`) — the real one |
| #8 | `configuration_save_service.py:283` | **Correct as written** — see below |

### The one that mattered: E12

The monthly donation task grants the mech $1.00 when its power has run to
zero, and the handler around that grant says, in a comment,
*"Continue anyway to send the message"* — exactly right, because the appeal has
nothing to do with whether the gift worked. But the tuple was
`(ValueError, TypeError, RuntimeError)`, and `add_system_donation` calls
`_heal_if_lagging`. `MechStateError` was in **none of the three tuples in that
file**, so it left the task entirely and the month's appeal was sent to
nobody — for a reason that had nothing to do with the appeal.

Second location of the same sentence as **E8**. That is what a scan is for:
by hand, E8 was found and the search stopped there.

### The one the scan got wrong: #1

`save_spam_protection` calls `spam_service.save_config(config)`. That is
`SpamProtectionService.save_config`, which returns a `ServiceResult` and
raises nothing of the kind — a **different method that happens to share a
name** with the config service's.

**The scan matches by name, and this is its limit.** It cannot tell two
`save_config` methods apart, and every hit therefore has to be read back to
the definition before it counts. One in nine was noise here; a bigger scan
would produce more. Recorded so the next person running it does not take the
hit list for a finding list.

### The one that was already right: #8

`_save_configuration_files` calls the legacy `save_config` wrapper, and
`ConfigService.save_config` **raises** `ConfigSaveError` rather than returning
`success=False`. That exception does escape the three handlers in that
method — and lands one level up in `save_configuration`'s
`except ConfigServiceError`, whose comment already names `save_config` as its
source. The operator gets an honest "Error saving configuration: …".

Worth stating plainly: **the scan hit is real and the code is correct.** A
handler being narrow is not a defect when the right handler is one frame up.

## Scan 2, second run — the 22 files no pass ever covered

The scan was rewritten as `scripts/review/scan_handlers.py` and pointed at the
22 files with no coverage evidence in `COVERAGE_BY_FILE.txt`. The rewrite
added one thing the first, ad-hoc version did not have: **propagation**. A
function that calls a raiser and does not catch it counts as a raiser too, up
to a depth (default 3), and the depth is printed with each hit.

That was not a refinement. The first version would have missed **E12**, the
finding it came out of: the handler there sits over `add_system_donation`,
which raises nothing itself — it calls `_heal_if_lagging` under the lock, and
that raises. One level of distance was enough to hide it from a reader, and
would have been enough to hide it from a direct-only scan.
`scan_handlers.py --selftest` re-runs the scan against the code as it stood
before E12 and fails if it no longer finds it. Measured: with propagation
switched off, the selftest goes red.

**17 hits, and one of them was the source of fourteen.**

| Finding | What |
|---|---|
| **E15** | `check_connectivity` — the function whose ONLY job is to say whether Docker is reachable — raised instead of answering when the daemon was actually gone. `DockerConnectionError` was in none of its four handlers. Measured in the running container. Fixing it at that one place closed **14 of the 17 hits**, because every one of them was downstream of it. |
| **E16** | `get_status`, the single-container refresh path, had the same gap with no pre-check above it to make up for it. The bulk path was already defended twice over (a connectivity pre-check, and review B25 turning a gathered exception into a named error result); this path had neither. |
| **E14** | Not a scan hit at all — found while reading one. See below. |

The two remaining hits are `config_service.py:499/506`, judged clean:
`TokenEncryptionError` is a `ConfigServiceError`, so it lands in the panel's
own `except ConfigServiceError`, and `_keep_bot_token_encrypted` runs at
line 419, before the write at 452 — nothing is half-saved.

### E14, found beside a hit rather than in one

Judging the `docker_control.py` hit meant asking what happens when a DDC
exception leaves a slash command. The answer was that **nothing happens**:
`app/bot/events.py` registered `on_command_error`, which is py-cord's
**prefix**-command event, and DDC has no prefix commands. Slash command errors
go to `application_command_error`, where py-cord's default prints to stderr and
never answers the user — so a failed command left the interaction thinking
forever.

That handler carries review C44, whose comment reads *"they pressed the button
and pressed again"*. C44 read the symptom correctly and installed the cure on
an event that never fires. `test_a_donate_cooldown_is_still_announced.py`
stayed green throughout, because it calls the handler function directly — a
fair way to test the logic, which was right. It never asked whether anything
calls it.

**This is the argument for reading around a hit rather than only at it.** The
scan pointed at a narrow handler in a status command. The defect was two files
away, in the wiring.

### Noted while judging #8, not repaired

`_save_server_order` (step 5) writes the server order file *before* the main
configuration is saved in step 6. If step 6 fails, the order file has already
been changed and the panel reports a failed save. A partial write, pre-existing
and unrelated to this scan. Not pursued.

## What the two scans say about the programme

Both scans came from the same observation — a sentence found three times by
hand — and both paid for themselves on the *second* instance of a sentence the
review had already found once. The technique is not "read everything again";
it is **take one confirmed finding and ask the machine where else it lives.**

The cost was under an hour each. The limit is that both are text scans: they
find shapes, not behaviour, and every hit has to be read back to the
definition before it counts as anything.

**And the second run taught the other half of it.** Seventeen hits came from
*one* defect — `check_connectivity` raising instead of answering — with
sixteen of them being places downstream that would have had to defend
themselves against a function that was already supposed to have done it. A
long hit list is not a long finding list, and chasing each hit where it lands
would have produced sixteen broad handlers instead of one honest return value.
**Follow the hits upstream before repairing any of them.**

## Closing the DDC-exception scan (2026-09-22)

The scan went **86 → 38** (a false positive in the scanner itself: it judged
each `except` clause alone, so a `try` closed by a handler that *does* catch
still reported the earlier clauses) **→ 29** (E43) **→ 20** (E45) **→ 14**
(E46) **→ 12** (E47) **→ 10** (E48) **→ 7** (E49).

Seven hits remain and none of them is a defect. Each was read back to the
definition; this is what each one is:

| Hit | Why it stays |
|---|---|
| `main_routes.py:461` | Name matching. `spam_service.save_config` is a different method from the `save_config` that raises, and it raises nothing. |
| `docker_client_pool.py:172` | By design since E48. The fast path deliberately lets `DockerConnectionError` past its own clause so the method's own handler answers it with a result — queuing a request that cannot be served would only buy it a 90-second wait. |
| `docker_client_pool.py:474` | `get_client_async` is a context manager with no result type. It raises on timeout too (line 512). Raising is its contract. |
| `docker_utils.py:438` | The scanner's known limit. This is a factory: `return get_docker_client_async(...)` hands back a context manager, and the raise happens at the **caller's** `async with`, not here. |
| `member_count/service.py:154` | Caught one frame up, by a handler that names this exact case: *"update_member_count heals first and can raise MechStateError since D1"* (review E8). |
| `donation_message_service.py:82` | Decided earlier, recorded as a decision. |
| `configuration_save_service.py:283` | Caught one frame up, in a handler whose own comment already names `save_config` as its source. |

### Two hits that closed without being touched

`docker_utils.py:534` and `:926` disappeared from the list without an edit at
either site, because the functions they call stopped raising. That is the
upstream rule from the previous section working in the other direction: repair
the source and the downstream hits close themselves. Sixteen of them did so in
the first run; two more did here.

### One hit that was a false positive for a reason no scan can see

`docker_utils.py:926` was read as real right up to the mutation probe. The
per-container handler in `test_docker_performance` lists only
`(DockerException, RuntimeError)`, and the two functions it calls raised a
`DockerConnectionError` — the shape matches exactly. It never escaped, because
of one keyword three lines above:

    asyncio.gather(info_task, stats_task, return_exceptions=True)

The exception arrives as a **value**. Reverting the handler I had added left
every test green, which is the whole reason to probe a fix before shipping it:
the change was not wrong, it was unjustified, and a handler nothing can
justify is a handler the next reader has to re-derive.

`test_the_performance_report_reaches_its_containers` now stands where the scan
cannot look — it fails if `return_exceptions=True` is ever removed.

### And one fix that would have made things worse on its own

E49 taught `get_docker_info` to answer `None` instead of raising. The
performance report read that raise, through the same `gather`, and wrote it
down as `"Info error: ..."`. Answering `None` correctly meant the report
started listing a container nobody could reach with a timing and **no errors**
— which reads as healthy.

The test caught it because it asked for the error text rather than for a
`dict`. `assert isinstance(result, dict)` would have stayed green through it.
